# Decisions

A running log of the choices made so far, newest last. Each one says what we chose
and why, so a future reader (including me) doesn't have to guess.

## Public, Apache-2.0, from the first commit
*2026-11-08*

The repo is public and licensed Apache-2.0 from its first commit. The history is part
of what the project shows, so there is nothing to tidy up before opening it.

## Application ID: `io.github.valnrys.teambayes`
*2026-11-08*

There is no personal domain, and a GitHub-based ID is free and suits an open-source
project. It matters because an Android app's ID can't change after its first upload
to Google Play.

## Every change is reviewed adversarially by two independent AI reviewers before it's pushed
*2026-11-08*

Each AI reviewer is asked to find what's wrong, not to approve. Two different reviewers
catch different things, and nothing reaches the public repo until both come back clean.

## Weng-Lin Thurstone-Mosteller, via openskill
*2026-11-08*

The rating model is the Weng-Lin Thurstone-Mosteller "full pairing" model, ported from
the open-source Python package openskill (MIT licence). The engine most apps use,
TrueSkill, is patented and trademarked, so we avoid it. Weng-Lin gives the same kind of
answer (a skill estimate plus how unsure we are) without that baggage.

## Per-game beta scaling
*2026-11-08*

Beta is how much one game's form can stray from true skill. It scales with the number
of players: `beta = (25/6) * sqrt(n/2)`. More players on the pitch means more room for luck, so a
bigger game should be treated as noisier than a one-on-one.

## Fixtures are the source of truth
*2026-11-08*

The Kotlin is checked against JSON files generated by openskill 6.2.0, to within 1e-9.
Tiny values in the tails of the curve are compared by relative error instead, because
an absolute 1e-9 would accept `0.0` for almost anything. Fixture points where a
one-bit change in the maths would flip the answer are dropped, since a correct port
could fail them by bad luck. If Kotlin and a fixture disagree, the Kotlin is wrong.
See [tools/fixtures/README.md](../tools/fixtures/README.md).

## Fixture generation needs Python 3.14 and the pure-Python openskill
*2026-11-08*

From Python 3.14, the normal distribution's `cdf` is computed in a way that stays
accurate in the lower tail; older versions lose it. And openskill's compiled wheels
bypass the generator's safety checks, so we install it from source.

## Copy openskill's quirks rather than fix them
*2026-11-08*

openskill has a few oddities, such as a tie-averaging step that always averages to
zero. We copy them exactly. The goal is to match the reference, and a "fix" would make
every fixture comparison ambiguous. Each quirk is written down in
[model.md](model.md).

## Zero runtime dependencies for `:engine`
*2026-11-08*

The engine uses only the Kotlin standard library. Fewer dependencies means less to
audit, no version clashes, and an engine that could be reused in a later iPhone
version. (Test-only libraries are fine.)

## Our own normal-distribution maths, with StrictMath
*2026-11-08*

We wrote `NormalDist` ourselves rather than add a maths library: `erfc` (a standard
error-function helper) is a translation of fdlibm's, and the inverse CDF follows
CPython's implementation of algorithm AS241. `exp` and `log` come from Java's
`StrictMath`, which gives the same bits on every JVM and Android phone. Tail accuracy
matters here: a cruder `erfc` was almost outside tolerance.

## Kotlin 2.4.21, Gradle 9.8.2, JDK 21 toolchain on the Java 17 API
*2026-11-08*

Versions are pinned, and the Gradle download's checksum is pinned too, so a swapped
download fails the build. We compile with JDK 21 but target Java 17 bytecode and the
Java 17 API, so the engine doesn't quietly use anything newer than Android supports.

## `rate` takes no per-game tau
*2026-11-09*

Tau is a small amount of uncertainty added before every game. openskill lets a caller
override it per call; we don't expose that, because the app never needs it. The model's
own value is used every time, so there is one setting in one place.

## Results are small named classes
*2026-11-09*

`rate` returns a `RatedTeams` and win chances come back as `WinProbabilities`, rather
than pairs. `result.teamA` reads better than `result.first`, and nobody has to remember
which side is which.

## Starting skill comes from a dragged ranking
*2026-11-09*

On first run the organiser drags players into a best-to-worst order, and that order
sets each starting skill, spaced evenly across 25 plus or minus two betas (about
16.7 to 33.3). Each end sits exactly one starting sigma from the centre, so the ranking matters
early, and a few real games outweigh it. A ranking is also easier to give than a score.

## The balancer is exhaustive up to 20 players
*2026-11-09*

A JavaScript balancer the author wrote earlier tried every split up to 18 players and
sampled above that. There are only 92,378 distinct splits at 20 players, which is cheap
to check in full, so we do. Sampling now starts when the number of possible splits
(after locks) exceeds 100,000, and the sample is uniform across both team sizes.
Players are capped at 64. Splits are ranked by predicted draw probability: the higher
the chance of a draw, the more even the game.

## Ratings are always replayed from scratch, never patched
*2026-11-09*

The app stores players and games, not ratings. Current ratings come from replaying
every game by when it was played, then when it was entered, then by id. Editing or
deleting an old game then just means replaying again, with no way for a stored rating to
drift out of step with the history.

## Android Gradle Plugin 9.5.1 with built-in Kotlin
*2026-11-16*

The app uses AGP 9.5.1, the latest stable release, on the pinned Gradle 9.8.2 (AGP needs
9.6.0 or newer). Since AGP 9.0, Kotlin support is built in, so the app does not apply the
`org.jetbrains.kotlin.android` plugin. Only the Compose compiler plugin is added, at the
same version as Kotlin.

## minSdk 26, compile and target SDK 37
*2026-11-16*

minSdk 26 (Android 8.0) lets launcher icons use a single adaptive-icon file and covers
almost every phone in use. Compile and target SDK are 37, the newest AGP 9.5.1 supports.

## The build fails on any unlisted permission
*2026-11-16*

TeamBayes is offline, so the app must never request INTERNET. A Gradle task,
`verifyAllowedPermissions`, sits inside the merged-manifest pipeline, so every build
that uses an app variant's manifest (APK, bundle, install) runs it first, not just `check`.
The androidTest APK has its own manifest, which is not checked. It
is an allowlist: it fails on any permission, from `<uses-permission>` or
`<uses-permission-sdk-23>`, except AndroidX's own `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`.
We do not strip permissions with `tools:node="remove"`, because that would silently hide a
library's request; a person should see it and decide.

## Backup is disabled
*2026-11-16*

`allowBackup` is false and the data-extraction rules exclude everything. No player data
should leave the phone through Google's cloud backup. The app will have its own JSON
export, which the user controls.

## The emoji2 font downloader is removed
*2026-11-16*

Compose pulls in `androidx.emoji2`, whose start-up initializer can ask a font provider
to download an emoji font. That is network activity by proxy, so its `meta-data` entry is
removed from the manifest. The app uses the system's emoji.

## No dynamic colour
*2026-11-16*

The app has a fixed Material 3 palette, light and dark by system setting (see "A dark-first
theme with bundled fonts" below).
Wallpaper-derived colours would make the app look different on every phone and make
screenshots inconsistent.

## Release shrinking is deferred
*2026-11-16*

R8 and resource shrinking will come with the release-signing work, so they can be
tested together on a signed build.

## On-phone balancing time
*2026-11-16*

Measured on a Pixel 9 Pro: balancing 18 players takes a median of about 66 ms, and 20 players
(the exhaustive limit) a median of about 270 ms. The work runs off the main thread, so the
screen stays responsive.

## Match day copies the original web version's flow
*2026-11-17*

The app's match day follows the original web version of this tool closely: the same
steps (roster, pick a split or make teams by hand, confirm), the same wording and the
same rules for moving and locking players. The group already knows that flow from real
nights, so familiarity is worth more than novelty. Where the app differs on purpose, a
comment in the code says why, so every divergence is a decision rather than drift.

## Three proposals, each with quality and win chances
*2026-11-17*

Generate shows the balancer's three most even splits, as the original did. Each card
shows a quality percentage and each side's chance of winning. The win chances are shown
by the owner's choice, although they aren't well calibrated yet: the ratings start as
guesses from a ranking, and the model has known biases (see [model.md](model.md)). They
are commentary only and never block anything. The two chances are rounded so they always
add up to 100.

## Quality is the draw chance over the draw chance at level totals
*2026-11-17*

`quality()` divides a split's predicted draw chance by the draw chance the same players
would have if both teams' total skill were exactly level. That gives 0 to 1, where 1.0 is
as even as these players could be, and it means the same thing for any roster. Every
split of one roster shares the same denominator, so quality ranks splits exactly as the
balancer's draw chance does. The original showed TrueSkill's match quality, which is
patented, so this measure is built from the model's own maths instead.

## Bibs and Non-bibs
*2026-11-17*

The two teams are called Bibs and Non-bibs, as on the pitch and in the original. In the
code, team A is always the Bibs and team B the Non-bibs.

## A dark-first theme with bundled fonts
*2026-11-17*

The palette, fonts and shapes follow the original web version. The dark scheme came
first and the light one is derived from it; the app still follows the phone's setting.
Instrument Serif, DM Sans and DM Mono are bundled in the app under the SIL Open Font
License (see [NOTICE](../NOTICE)), because downloadable fonts arrive through a provider
app over the network. Where the original's colours were too faint, they were lightened
to meet WCAG AA: muted text (`#7B97B4` instead of `#5B7896`, which is only 4.2:1 on the
background) and the error red (`#F87171` instead of `#EF4444`, only 4.3:1 on raised
cards). In the dark theme, control borders use `#5B7896`; in the light theme, `#64788E`. Both
reach the 3:1 that borders need on every surface.

## Moving a player clears their lock
*2026-11-17*

This is a deliberate divergence from the original, which left locks alone when you
edited a split. A lock means "keep this player on this side". After a move, the old lock
would point at the side they just left, so the chip would show a lock that doesn't match,
and the next re-generate would quietly move them back. Clearing it keeps what the screen
shows and what re-generate does in step.

## Generate is enabled from two players and explains why it can't run
*2026-11-17*

Both roster buttons unlock at two ticked players, as in the original. The manual board
works from two, but the balancer needs four. Rather than grey out Generate with no
reason, tapping it with two or three players shows the engine's own explanation, which
also suggests making teams by hand.

## Taps while generating either cancel the run or are ignored
*2026-11-17*

A tap that changes who's playing (ticking, adding a player, going back, the manual
board) cancels the balancer run, because its answer would be for the wrong people. A
tap that changes the teams on show (moving, locking, choosing a card, Continue,
re-generate) is ignored until the new proposals arrive, because they would replace it.
The balancer's maths doesn't stop when cancelled, but a cancelled run can never publish
its result.
