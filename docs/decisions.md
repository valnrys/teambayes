# Decisions

A running log of the choices made so far, newest last. Each one says what we chose
and why, so a future reader (including me) doesn't have to guess.

## Public, Apache-2.0, from the first commit
*2026-11-08*

The repo is public and licensed Apache-2.0 from its first commit. The history is part
of what the project shows, so there is nothing to tidy up before opening it.

## Application ID: `io.github.valnrys.teambayes`
*2026-11-08*

There is no personal domain, and a GitHub-based ID is free and suits an open-source
project. It matters because an Android app's ID can't change after its first upload
to Google Play.

## Every change is reviewed adversarially by two independent reviewers before it's pushed
*2026-11-08*

Each reviewer is asked to find what's wrong, not to approve. Two different reviewers
catch different things, and nothing reaches the public repo until both come back clean.

## Weng-Lin Thurstone-Mosteller, via openskill
*2026-11-08*

The rating model is the Weng-Lin Thurstone-Mosteller "full pairing" model, ported from
the open-source Python package openskill (MIT licence). The engine most apps use,
TrueSkill, is patented and trademarked, so we avoid it. Weng-Lin gives the same kind of
answer (a skill estimate plus how unsure we are) without that baggage.

## Per-game beta scaling
*2026-11-08*

Beta is how much one game's form can stray from true skill. It scales with the number
of players: `beta = (25/6) * sqrt(n/2)`. More players on the pitch means more room for luck, so a
bigger game should be treated as noisier than a one-on-one.

## Fixtures are the source of truth
*2026-11-08*

The Kotlin is checked against JSON files generated by openskill 6.2.0, to within 1e-9.
Tiny values in the tails of the curve are compared by relative error instead, because
an absolute 1e-9 would accept `0.0` for almost anything. Fixture points where a
one-bit change in the maths would flip the answer are dropped, since a correct port
could fail them by bad luck. If Kotlin and a fixture disagree, the Kotlin is wrong.
See [tools/fixtures/README.md](../tools/fixtures/README.md).

## Fixture generation needs Python 3.14 and the pure-Python openskill
*2026-11-08*

From Python 3.14, the normal distribution's `cdf` is computed in a way that stays
accurate in the lower tail; older versions lose it. And openskill's compiled wheels
bypass the generator's safety checks, so we install it from source.

## Copy openskill's quirks rather than fix them
*2026-11-08*

openskill has a few oddities, such as a tie-averaging step that always averages to
zero. We copy them exactly. The goal is to match the reference, and a "fix" would make
every fixture comparison ambiguous. Each quirk is written down in
[model.md](model.md).

## Zero runtime dependencies for `:engine`
*2026-11-08*

The engine uses only the Kotlin standard library. Fewer dependencies means less to
audit, no version clashes, and an engine that could be reused in a later iPhone
version. (Test-only libraries are fine.)

## Our own normal-distribution maths, with StrictMath
*2026-11-08*

We wrote `NormalDist` ourselves rather than add a maths library: `erfc` (a standard
error-function helper) is a translation of fdlibm's, and the inverse CDF follows
CPython's implementation of algorithm AS241. `exp` and `log` come from Java's
`StrictMath`, which gives the same bits on every JVM and Android phone. Tail accuracy
matters here: a cruder `erfc` was almost outside tolerance.

## Kotlin 2.4.21, Gradle 9.8.2, JDK 21 toolchain on the Java 17 API
*2026-11-08*

Versions are pinned, and the Gradle download's checksum is pinned too, so a swapped
download fails the build. We compile with JDK 21 but target Java 17 bytecode and the
Java 17 API, so the engine doesn't quietly use anything newer than Android supports.

## `rate` takes no per-game tau
*2026-11-09*

Tau is a small amount of uncertainty added before every game. openskill lets a caller
override it per call; we don't expose that, because the app never needs it. The model's
own value is used every time, so there is one setting in one place.

## Results are small named classes
*2026-11-09*

`rate` returns a `RatedTeams` and win chances come back as `WinProbabilities`, rather
than pairs. `result.teamA` reads better than `result.first`, and nobody has to remember
which side is which.

## Starting skill comes from a dragged ranking
*2026-11-09*

On first run the organiser drags players into a best-to-worst order, and that order
sets each starting skill, spaced evenly across 25 plus or minus two betas (about
16.7 to 33.3). Each end sits exactly one starting sigma from the centre, so the ranking matters
early, and a few real games outweigh it. A ranking is also easier to give than a score.

## The balancer is exhaustive up to 20 players
*2026-11-09*

A JavaScript balancer the author wrote earlier tried every split up to 18 players and
sampled above that. There are only 92,378 distinct splits at 20 players, which is cheap
to check in full, so we do. Sampling now starts when the number of possible splits
(after locks) exceeds 100,000, and the sample is uniform across both team sizes.
Players are capped at 64. Splits are ranked by predicted draw probability: the higher
the chance of a draw, the more even the game.

## Ratings are always replayed from scratch, never patched
*2026-11-09*

The app stores players and games, not ratings. Current ratings come from replaying
every game in date order. Editing or deleting an old game then just means replaying
again, with no way for a stored rating to drift out of step with the history.
